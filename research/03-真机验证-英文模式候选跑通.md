- 验证日期：2026-11-01

- 结论：**成功。英文模式下可以产出中文候选，全程纯 Lua，未改一行 C++。**

## 一、先纠正一个错误

**验证 01 的结论有一处是错的，必须更正。**

我当时说「英文模式下按键会 `PushInput` 进入输入缓冲」，并引用了 `ascii_composer.cc` 第 253-255 行。这段代码本身没错，但我**漏看了它前面的分支**。

真实控制流是这样的（`ascii_composer.cc`）：

```cpp
// 第 242-245 行 —— 我之前漏掉的分支
// 9. 全域純西文態且無輸入：極速直通操作系統
if (ascii_mode && !ctx->IsComposing()) {
  return kRejected;      // ← 直接放行给操作系统，Rime 不管了
}

// 第 247-258 行 —— 我之前引用的分支
if (ch >= 0x20 && ch <= 0x7e) {
  raw_keys_.push_back(ch);
  if (ascii_mode && ctx->IsComposing()) {   // ← 要求"已经在输入中"
    ctx->PushInput(ch);
    return kAccepted;
  }
  return kNoop;
}
```

关键在 `!ctx->IsComposing()`：**刚进入英文模式时输入缓冲是空的，所以第一个字母就被 `kRejected` 直接放行，根本没有进入 Rime。**

实测验证了这一点：英文模式下打字，`preedit` 为空、候选数为 0，输入串完全没进引擎。

**教训**：静态读代码时，看到一段逻辑成立就下结论，是危险的。必须把同一个函数的前置分支全部看完。这次是真机测试把错误逼出来的。

## 二、真正的解法：抢在 ascii_composer 之前

既然按键在 `ascii_composer` 就被放行了，那就**排到它前面去**。

### 关键发现：Lua 能写输入缓冲

`librime-lua/src/types.cc`，Context 暴露的方法里有：

```cpp
{ "push_input", WRAP(push_input) },
{ "pop_input", WRAPMEM(T::PopInput) },
{ "select", WRAPMEM(T::Select) },
{ "confirm_current_selection", WRAPMEM(T::ConfirmCurrentSelection) },
```

`push_input` 意味着 Lua 可以**主动把字符塞进输入缓冲**，这正是绕开 `kRejected` 的钥匙。

### 实现

在 `rime.lua` 里写一个前置处理器：

```lua
function pipi_ascii(key, env)
  local ctx = env.engine.context
  if not ctx:get_option("ascii_mode") then
    return 2                        -- kNoop，交给后面的处理器
  end
  local kc = key.keycode
  local is_letter = (kc >= 97 and kc <= 122) or (kc >= 65 and kc <= 90)
  if not is_letter then
    return 2                        -- 空格、回车、退格等原样放行
  end
  ctx:push_input(string.char(kc))   -- 截回输入缓冲
  return 1                          -- kAccepted
end
```

配置上把它插到处理器列表最前面：

```yaml
patch:
  "engine/processors/@before 0": "lua_processor@pipi_ascii"
  "engine/translators/+":
    - "lua_translator@pipi_test"
```

部署后产物确认顺序正确：

```yaml
processors:
  - "lua_processor@pipi_ascii"   ← 插到第一位
  - ascii_composer               ← 原来的第一道关
  - recognizer
  ...
```

## 三、实测结果

用 Python 直接驱动 `rime.dll`（`RimeCreateSession` / `RimeSimulateKeySequence` / `RimeGetContext`），在真实引擎里跑：

### 测试 A · 中文模式打 `nihao`（基线）
```
preedit='ni hao'  候选数=5
1. 你好   2. 妳好   3. 逆号   4. 拟好   5. 你
```
中文输入未被破坏。

### 测试 B · 英文模式打 `woyaochifan`（核心）
```
ascii_mode = 1
preedit='woyaochifan'  候选数=1
1. 皮皮|woyaochifan    // seg=0-11 len=11
```
**英文模式下，按键被截回、翻译器被调用、候选正常显示。**

### 测试 C · 英文模式打 `meeting`（误伤检查）
```
preedit='meeting'  候选数=1
1. 皮皮|meeting
```
说明目前是**无条件产出**，正常英文单词也会被介入。这是需要后续用「是否像合法拼音」来判断的事，属于调优范畴。

## 四、阶段结论

| 问题 | 答案 |
|---|---|
| 纯 Lua 能不能在英文模式下产出候选 | **能，已实测** |
| 需不需要改 C++ | **不需要** |
| 中文输入会不会被破坏 | 不会 |
| 最大遗留问题 | 候选排序与误伤控制 |

**"能不能做"到此已经彻底确认。** 剩下的全部是产品质量问题：

1. `皮皮|woyaochifan` 目前只是个占位符，要换成真正的拼音转汉字（用词库 + 八股文语言模型）
2. 英文模式下怎么选中文候选——数字键被 `ascii_composer` 吃掉了，需要另找按键方案
3. 怎么判断一串字母"像不像拼音"，避免 `meeting` 也被当成拼音
